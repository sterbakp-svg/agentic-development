# Spike T-020: platform limits for the pilot

Status: **desk part done (2026-11-15); hands-on test by the product owner open.** Options from `docs/05-mvp-copilot-studio.md`: A (full prompt), B (examples without rendered text), C (Azure Function with `packages/core`).

Sources: `docs/research/T-020-platform-facts.md` (fact IDs in brackets). Test steps: `docs/checklists/T-020.md`. Paste files and helpers: `pilot/copilot-studio/spike/`.

## 1. Recommendation

**Option A, on condition of the test.** Choose B only if the prompt editor refuses the option A text. Choose C only if one of these happens:

- fewer than 9 of 10 runs per golden profile pass the reference validator (this is the T-023 AC), or
- the flow cannot be built with checks that are at least as strict as the reference (section 4), or
- the flow needs more than 100 seconds.

If the agent rewrites the text the flow returns, that is no reason for C: the tool can be set to "Send specific response" with the output variable [5.6].

Reasons:
- No documented cap on prompt instructions. The only documented limit is the model context window: 128K tokens for the default model GPT-4.1 mini [1.1, 1.5]. Option A has 44,478 characters, about 12,000 tokens at the ratio of 3.8 characters per token in a Microsoft example [1.9].
- B saves about 11,300 characters, but it removes the rendered examples, which show the model the target text. Use B only if size forces it.
- C needs an Azure subscription (H-3, Q-04). It moves pilot work into phase 2 before the pilot has proved the idea.

## 3. What the repository already proves

`node pilot/copilot-studio/spike/build.mjs` runs three self-checks and stops on any failure:

- A port of the reference renderer gives byte-identical output for both golden examples.
- A JavaScript emulation of the flow's own method (whole-body `replace()`, the two fixed line drops, `trim`) also gives byte-identical output. So the method in `flow-expressions.txt` is correct; the hands-on test checks only that the Power Automate functions behave like their JavaScript counterparts.
- The emulated slot checks pass both golden slot sets and catch all 4 reference errors of `evals/negative/injection-slots.json` (line break and `#` in `tools`, "ignore previous" and automatic sending in `discretion_rule`). The guardrail and heading literals are checked against `reference/composer_ref.py` and both golden outputs.

## 4. Validator parity (Q-13, R-5)

Rule for the pilot I propose: **the flow may be stricter than the reference, never weaker.** Every reference error must have a flow check that rejects at least the same inputs.

| Reference check (`reference/composer_ref.py`) | Flow check | Parity |
|---|---|---|
| `{{` or `}}` in a slot or left in the text | `contains` | exact |
| line break in a slot (`[\r\n]`) | `contains` with `%0A` and `%0D` | exact |
| backtick in a slot | `contains` | exact |
| heading marker `^\s*#` (multiline) | `contains` of `#` anywhere in the slot | **stricter**: no dependency on what `trim` removes (Python `\s` includes U+001C to U+001F). Golden slots contain no `#`; a slot like "C# reviews" would be rejected |
| `ignore (all\|any\|the\|previous\|above)`, case-insensitive | replace ſ, K (Kelvin sign), İ, ı with s, k, i, i, then `toLower` + `contains` per phrase | exact or stricter. Python `re.I` folds exactly these four non-ASCII letters to ASCII (checked over all code points) |
| `disregard`, case-insensitive | same folding, then `toLower` + `contains` | exact or stricter |
| `\b(send\|forward\|delete\|move)\b[^.;]*\b(automatically\|without (asking\|review))` | `toLower` + `contains` of "automatically", "without asking", "without review" anywhere in the slot | **stricter**: rejects these words even without a send verb; same folding. Golden slots pass |
| slot length, instruction length | `length()` against limits from `template.json` | exact if `length()` counts code points; stricter if it counts UTF-16 units; weaker only if it counted grapheme clusters (test, `length_test`) |
| guardrail lines, section headings | `contains` | exact |
| missing slot, empty required slot, inline optional slot starts with a space, description, starters, name | not in the spike flow; plain string or count checks | expressible; T-024 builds them |
| placeholders `[...]` declared in `placeholders_left` | not in the spike flow; without regex it needs `split` on `[` and then on `]` | expressible; T-024 builds it |
| warning: instructions above `instructions_target_chars` | not in the spike flow; `length()` against the limit from `template.json` | expressible; T-024 adds a `warnings` output |
| warning: email address in a slot (`[\w.+-]+@...`) | `contains('@')` would be a stricter warning | approximate; warning only, not a guardrail |

Result: all guardrail checks can be expressed as exact or stricter checks. Option C is **not** needed for validator parity if the test confirms that `length()` counts code points or UTF-16 units. The price of "stricter" is a few false rejections (a `#` in a slot, "automatically" without a send verb); the T-023 AC (9 of 10 runs pass) shows whether that matters.

Gap found in the reference, outside this ticket: the computed slot `org_rule` holds user text, but the reference does not run the forbidden-content checks on it (Q-18).

## 5. Open points for the hands-on test

1. Does the prompt editor accept 44,478 characters (option A)? Are `{{...}}` markers shown as plain text?
2. Can a prompt tool be set to JSON output? Does the agent get usable JSON? Runs that pass the validator, out of 10 per golden profile.
3. Does the flow render both goldens byte-identical? `length_test` result. Does the injection case fail with all 4 errors?
4. Does the agent pass the flow input and output unchanged, within 100 seconds?
5. Does the VS Code extension install, sign in, clone, push and pull on macOS arm64? If not, does the `pac` route work (part 5b)?
6. Which agent type does the environment create (standard custom agent needed)?
