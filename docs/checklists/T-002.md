# Checklist T-002: turn on CI protection for `main`

Who: product owner (repository admin). Time: about 15 minutes.
Repository: `github.com/sterbakp-svg/agentic-development`.

## 0. Status

Q-17 is resolved: the repository is public since 2026-11-14. Rulesets, secret scanning and push protection are free for public repositories. **All steps are done (2026-11-14).** The lead did parts A to D with the owner's approval, through the GitHub API: PR #1 merged, ruleset `main protection` created, proof with PR #2 (blocked, closed), security settings on. Keep this checklist as the reference for a new repository.

## A. Push and first run

1. Push the branch `t-002-ci-pipeline` (or the branch the lead gives you) to GitHub.
2. Open a pull request into `main`. Title: `T-002: CI pipeline`.
3. Open the **Checks** tab of the pull request. Check: four jobs run and turn green: `checks`, `audit`, `secret-scan`, `reference`.
4. If a job is red, do not merge. Send the job log to the lead.
5. Merge the pull request. Check: the same four jobs run once more on `main`.

A job name only appears in the ruleset search (step 9) after it has run once. So do part A first.

## B. Branch ruleset on `main`

6. Go to **Settings > Rules > Rulesets > New ruleset > New branch ruleset**.
7. Ruleset name: `main protection`. Enforcement status: **Active**.
8. Target branches: **Add target > Include default branch**.
9. Turn on these rules and nothing weaker:
   - **Restrict deletions**: on.
   - **Require a pull request before merging**: on. Required approvals: 0 is fine while you work alone; set 1 when a second person joins.
   - **Require status checks to pass**: on. Turn on **Require branches to be up to date before merging**. Add these checks by name: `checks`, `audit`, `secret-scan`, `reference`.
   - **Block force pushes**: on.
10. Bypass list: leave it empty.
11. Click **Create**.

## C. Prove that a failing test blocks the merge

12. Create a branch: `git switch -c test-ci-block`.
13. In `packages/core/src/index.test.ts` change `toEqual([])` to `toEqual(['x'])`. This breaks only the test; lint and type check stay green. Commit and push.
14. Open a pull request into `main`.
15. Check: job `checks` is red, and the **Merge** button says that required checks have not passed. The merge is blocked.
16. Try `git push origin test-ci-block:main`. Check: GitHub refuses it (protected branch).
17. Close the pull request without merging. Delete the branch.

## D. Secret scanning, Dependabot and fork pull requests

The `secret-scan` job (gitleaks) stays. GitHub secret scanning adds push protection: a known secret is refused before it reaches GitHub.

18. Go to **Settings > Code security** (or **Advanced Security**).
19. Turn on **Secret scanning**.
20. Turn on **Push protection**.
21. Turn on **Dependabot alerts**. Dependabot version updates are already set in `.github/dependabot.yml`; check under **Insights > Dependency graph > Dependabot** that the weekly runs are listed.
22. Check: Secret scanning, Push protection and Dependabot alerts show **Enabled**.
23. Go to **Settings > Actions > General > Approval for running fork pull request workflows from contributors**. Choose **Require approval for all external contributors**. Click **Save**. Reason: in a public repository anyone can open a pull request, and CI would run their code.

## Notes

- The audit job ignores one known dev-only finding (GHSA-g3hv-75wg-m249). It is recorded as R-A1 in `docs/08-open-questions.md`. Remove the ignore in `package.json` when a fixed version exists.
- `audit` is a required check. A new upstream advisory can turn it red on a pull request that changed nothing. Then tell the lead; do not bypass the rule.
- Evals are not part of CI (Q-16). The lead runs them by hand.
